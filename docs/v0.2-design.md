# OpenDot v0.2 design: pull requests, a built-in browser and MCP connectors

> [!NOTE]
> This is the design record of version 0.2. Later versions removed approvals,
> rules and the reviewer: the host now runs every action the model proposes.
> See [how-it-works.md](how-it-works.md) for the current design.

OpenDot v0.2 adds three features and keeps the v0.1 rule that the model only
proposes. The model can now edit a private copy of a GitHub repository and
propose a branch, a pull request, an issue or a comment. It can use a Chromium
browser inside its step container. It can call tools on MCP servers, with FactIQ
available as a built-in connector. The host still holds every token. Every
outward action still goes through host-built actions, rules, a reviewer that
fails closed, and an approval bound to the exact payload. A v0.1 config file and
a v0.1 database work without changes, and every new feature is off by default.

## The trust boundary does not move

**No new feature gives the model a credential or a direct outward path.**

- GitHub: the model edits files in a copy of the repository. The copy's `.git`
  folder is mounted read-only, so the model cannot commit, change remotes or
  add hooks. The host makes the commit, runs the configured checks and pushes
  only after approval. The GitHub token never enters a container.
- Browser: Chromium runs inside the step container, under the same network
  setting as the model CLI (`sandbox.network`). It has no cookies, no saved
  logins and no host credentials. It does not add a new way out of the
  container; it uses the same network the container already has. Tools that
  run page scripts, upload files or read cookies and storage are left out of
  the default tool list.
- MCP connectors: the host connects to each server and holds its token. The
  container sees only a unix socket per connector. Tools marked `read` run
  directly and every call is logged. Tools marked `write` are not given to the
  model as tools. The model proposes them as actions (`mcp.<server>.<tool>`),
  and they go through rules, review and approval.

## How a work step runs with extensions

**Extensions prepare the step on the host and clean up after it. They never
start the model and never send anything outward.**

1. The orchestrator calls `StepExtensions.begin(ctx)`. For a work step with at
   least one active feature, it makes a step token (12 hex characters) and a
   run folder `<state_root>/runs/task-<id>/<token>` with mode 0700.
2. Each extension adds to the `StepPlan`: host mounts, MCP server entries,
   fixed environment values and notes for the prompt. The order is GitHub,
   browser, gateway.
3. The host checks every mount (`check_host_mounts`) and starts the container
   with the extra mounts and MCP servers.
4. After the step, `StepExtensions.finish` links the step's connector calls to
   the attempt and runs each extension's clean-up in reverse order. A failed
   clean-up is recorded as the task event `extension.cleanup_failed` and does
   not stop the others.

Review and reflect steps get no plan: no repository, no browser and no
connectors.

### Container folders

| Container path | Host source | Access |
| --- | --- | --- |
| `/opendot/repos/<name>` | `<state_root>/worktrees/task-<id>/<name>` | read-write |
| `/opendot/repos/<name>/.git` | the same copy's `.git` | read-only |
| `/opendot/run/artifacts` | a folder under the step's run folder | read-write |
| `/opendot/mcp` | a folder under the step's run folder | read-only |
| `/opendot/instructions/<name>` | `<state_root>/connectors/<name>/...` | read-only |

`check_host_mounts` refuses a mount that is not a real folder strictly inside
its base folder, that reaches the base through a symbolic link below the state
root, or that is outside a `task-<id>` folder (except instructions). Only
repository copies and the artifacts folder may be writable. A repository copy
must hold a real `.git` folder.

## GitHub: copies, branches and pull requests

**Each task gets its own clone of each configured repository. The host commits
and pushes; the model only edits files.**

- `<state_root>/repos/<name>` is a control clone that the host fetches.
- `<state_root>/worktrees/task-<id>/<name>` is made with `git clone --local`
  from the control clone at the default branch, on the first work step of the
  task, and reused by later steps.
- Host git commands on a copy run with `-c core.hooksPath=/dev/null` and
  `-c core.fsmonitor=false`, never recurse into submodules, refuse a nested
  `.git` entry and use `lstat` for size and mode checks. Files in the copy can
  be symbolic links that point at host paths.
- Preparing `github.push_branch` or `github.open_pr` makes the commit on the
  host, runs the repository's `checks` in a container on the copy with the
  repository's `check_network`, and records the tree hash, the diff summary
  and the check results in the payload. The reviewer and the operator see that
  payload. Running the action checks the tree hash again. If a later step has
  changed the copy, the action is refused and must be prepared again.
- `prepare` commands from the repository config run once after the copy is made,
  in a container with `sandbox.network`.
- Files that match `github.forbidden_files` (for example `.github/workflows/`)
  or are larger than `github.max_file_kib` stop the push.
- A repository whose visibility is public, or whose text matches
  `github.private_markers`, gets a stricter review note: public text must not
  carry private information.
- Every publication has a marker (a hidden line in the pull request or issue
  body) and a row in `github_publications`. Before opening a pull request the
  host looks for an open pull request with the same head branch, then for the
  marker in open pull request bodies. The row is the local guard against
  duplicates; the marker is the remote one.

`github.push_branch` and `github.open_pr` always ask (fixed floor). Issues and
comments ask by default.

## Browser

**Chromium and the Playwright MCP server are part of the step image, and the
browser is one more stdio MCP server in the step.**

- The image adds Chromium and `@playwright/mcp` version 0.0.83 (its command is
  `playwright-mcp`; its tools are named `browser_*`).
- With `browser.enabled = true`, each work step gets an MCP entry named
  `browser`, limited to `browser.tools`, a shared memory size of
  `browser.shm_size` and an artifacts folder for screenshots.
- `browser.allowed_origins` passes the Playwright origin list. It is a
  convenience, not a security boundary; the container network is the boundary.

## MCP connectors and FactIQ

**The host runs one gateway per step. The container reaches it through a unix
socket and a small bridge script, so no port and no token enter the
container.**

- For each connector, the host opens a unix socket in the step's `mcp` folder
  and copies a standard-library Python bridge script next to it. The model CLI
  starts `python3 /opendot/mcp/bridge.py /opendot/mcp/<name>.sock` as a stdio
  MCP server.
- A unix socket path is limited to 108 bytes. The host binds the socket through
  `/proc/self/fd/<folder fd>/<name>.sock` when the full path is too long.
- The gateway lists only the connector's allowlisted `read` tools, forwards the
  calls with the host's token, caps the result at `gateway.max_result_kib` and
  the time at `gateway.call_timeout_seconds`, and logs every call in
  `gateway_calls`.
- `write` tools become actions named `mcp.<server>.<tool>` and always ask.
- FactIQ is a preset: `factiq.enabled = true` adds the connector
  `https://api.factiq.com/mcp` with its read tools. `send_feedback` is added as a
  write action only with `factiq.feedback = true`. The key comes from the
  environment variable named in `factiq.api_key_env`, or from
  `opendot connectors login factiq` with `factiq.auth = "oauth"`.
- The guidance files from the public
  [factiq-plugin](https://github.com/defog-ai/factiq-plugin) (MIT licence) are
  fetched at a fixed commit into `<state_root>/connectors/factiq/instructions/`
  with its licence file, and mounted read-only for the model.

## Database version 2

**Five new tables. A version 1 database is upgraded in place on open; a newer
database is refused.**

| Table | Holds |
| --- | --- |
| `repositories` | each configured repository, its control clone, visibility and last fetch |
| `worktrees` | each task's copy: path, base commit, branch, status |
| `github_publications` | each push, pull request, issue or comment, keyed by its marker |
| `gateway_calls` | each connector call: server, tool, mode, arguments, status, size, time |
| `connector_tokens` | OAuth tokens for connectors, in the 0600 database file |

## Docker from a snap package

**Snap Docker works with two settings. It refuses the `no-new-privileges`
option, and it cannot see mount sources under `/tmp`.**

- Set `sandbox.no_new_privileges = false` and keep the state root and the
  read-only mounts outside `/tmp`. `sandbox.detect_snap_docker` and
  `snap_docker_problems` report what is wrong.
- Tested on snap Docker: a read-only `.git` mount on top of a writable copy,
  and a unix socket under the home folder that a container connects to, both
  work.
- Without `no-new-privileges`, a setuid program in the image could change its
  user id inside the container. All capabilities are still dropped and the root
  file system is still read-only. The step image should remove setuid and
  setgid bits; until it does, the docs make no claim that it has none.

## Changes from the first plan

**Two parts differ from the first plan, both because the container could not
use the first form.**

- Task copies use `git clone --local`, not `git worktree`. A `git worktree`
  copy has a `.git` file that holds the host path of the main repository, and
  that path does not exist inside the container.
- The gateway uses a unix socket and a bridge script, not a host port with a
  bearer token. A port would be reachable by anything on the Docker network,
  and the token would have to enter the container.

## Open checks

- Codex: the option `default_tools_approval_mode = "approve"` is accepted by the
  config parser. A live step must confirm that it lets allowlisted tools run
  without a prompt.
- Claude Code: a live step must confirm that `--allowedTools` accepts
  `mcp__<server>__<tool>` names with `--permission-mode dontAsk`.
